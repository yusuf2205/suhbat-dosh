# Звонки: качество, TURN и ограничения

## Что реализовано

| Область | Как сделано |
|---|---|
| Транспорт | стандартный WebRTC браузера/WebView; собственных кодеков и протоколов нет |
| Звук | Opus (приоритет в списке кодеков), эхоподавление, шумоподавление, АРУ — включаются через ограничения `getUserMedia`; можно отключить в «Настройки → Звук и видео» |
| Видео | цель 1080p / 30 кадров/с; кодеки: VP8 → H.264 → VP9 → остальные (аппаратное кодирование использует сам браузер/ОС) |
| Адаптация | раз в 2 с считаются RTT, джиттер, потери, исходящая пропускная способность; лестница 1080p30 → 720p30 → 540p24 → 360p15 → 270p12; **сначала снижается видео, голос не затрагивается** (приоритет и 64 кбит/с для аудио) |
| Режимы | «Авто», «Высокое качество» (позже и менее охотно снижает, не ниже 540p), «Экономия трафика» (360p15) |
| Устройства | выбор микрофона, динамиков (там, где браузер поддерживает `setSinkId`), камеры; проверка до звонка (уровень микрофона, камера, тестовый звук); переключение камеры, автофокус (если камера поддерживает) |
| Устойчивость | при потере связи — ICE restart без завершения звонка; сервер даёт 25 с на возвращение устройства (смена Wi-Fi ↔ мобильная сеть, сворачивание приложения); индикатор качества и подсказка «слабое соединение» |
| Метрики | в конце звонка отправляются только числа (RTT, потери, джиттер, битрейт, разрешение, fps, кодек, прямое/TURN, число переподключений) → журнал администратора. Содержимое разговора нигде не записывается |

## Что проверено, а что нет

Проверено автоматически (Chromium с виртуальными камерой и микрофоном, localhost):
согласование аудио и видео в обе стороны, декодирование кадров, смена параметров, выбор VP8, метрики,
переподключение при кратковременной потере WebSocket, юнит-тесты логики адаптации.

**Не проверено** на реальных устройствах: Android/iOS/macOS/Linux, разные модели камер и микрофонов,
Bluetooth-гарнитуры, эхо при динамиках, слабый интернет/потери/смена сети, перегрев. Поэтому
«HD-качество» и «шумоподавление» в приложении не заявляются как проверенные: цель — 1080p30, но
фактическое качество зависит от камеры, процессора и сети (в тесте на виртуальной камере: 960×540@20).

## TURN (когда прямое соединение невозможно)

По умолчанию используются публичные STUN-серверы; около 80–90% звонков соединяются напрямую.
Для остальных (строгий NAT, корпоративные сети, часть мобильных операторов) нужен TURN-сервер.

Оценка вашего NAS (DXP4800 Plus): 6 ядер, 64 ГБ ОЗУ, сеть 1 Гбит/с, загрузка ~2 (76 контейнеров).
TURN только пересылает пакеты (без перекодирования), поэтому процессор не узкое место; ограничение —
**исходящая скорость домашнего интернета**: один видеозвонок 720p через TURN ≈ 2 × 1,5–2,5 Мбит/с.
При 20 Мбит/с исходящей — 4–6 одновременных звонков через ретранслятор.

Включение (нужен проброс UDP-портов на роутере — через Cloudflare Tunnel TURN работать не может):

1. Роутер: UDP 3478 и UDP 49160–49200 → 192.168.1.8.
2. `.env`: `TURN_EXTERNAL_IP` (ваш белый IP), `TURN_USERNAME`, `TURN_CREDENTIAL` (длинный случайный пароль),
   `TURN_URLS=turn:suhbat-dosh.uz:3478` — и в DNS-записи `suhbat-dosh.uz` Cloudflare **без** проксирования
   (серый облачок) для отдельного имени, например `turn.suhbat-dosh.uz`; тогда `TURN_URLS=turn:turn.suhbat-dosh.uz:3478`.
3. `docker compose --profile turn up -d`.

## Групповые звонки

Не реализованы. Для групп нужен SFU (рекомендуется LiveKit или mediasoup): отдельный контейнер,
отдельные порты, передача медиа независимо от API сообщений. Архитектура уже разделяет сигнализацию и медиа,
так что это добавляется без переделки чатов.
